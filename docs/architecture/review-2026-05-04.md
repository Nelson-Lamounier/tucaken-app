## 1. What is good

- **TanStack stack alignment.** Router (file-based), Query (query-keys factory in `lib/api/`), Start (`createServerFn` per server file), Form, Devtools — all wired.
- **Server-fn modularity.** `src/server/<domain>.ts` is one of the cleanest parts of the repo. Each domain isolated; `_api-client.ts` shared; auth via `auth-guard.ts` / `session.ts`. Tests mock `@tanstack/react-start` cleanly.
- **Feature slices.** `src/features/<name>/{components,hooks}` is a real boundary that maps 1-to-1 with routes for 12 of 13 features.
- **Cross-cutting `lib/`.** Observability (Faro/OTel/Pyroscope/Pino), Zustand stores, query-keys factory, shared types — all properly hoisted out of feature folders. This is the right call.
- **TypeScript strictness.** `strict`, `noUnusedLocals`, `noUnusedParameters`, `noUncheckedSideEffectImports`. Nothing turned off.
- **Conventions doc per feature.** `features/account/README.md`, `features/home/README.md` show the team understands feature boundaries.

## 2. Known smells (in priority order)

### 2.1 ✅ `features/account/` wired (2026-05-04) — server fns still TODO

- **Wired by:**
  - `src/app/_dashboard.billing.tsx` → `/billing`, mounts `BillingPage`.
  - `src/app/_dashboard.settings.index.tsx` → `/settings`, mounts `SettingsPage` (coexists with `/settings/github`).
  - Sidebar links added in `AppLayout.tsx#settingsNavigation`: **Settings**, **Billing**, **GitHub**.
- **Data layer (interim):**
  - `src/features/account/defaults.ts` — seed `Billing` + `Settings`.
  - `src/features/account/hooks/use-billing.ts`, `use-settings.ts` — local `useState` + `update(patch)` reducer matching the README controlled-component contract.
- **TODO before this is "real":**
  1. Add server fns in `src/server/me.ts` (or new `src/server/billing.ts`, `src/server/settings.ts`): `getBillingFn`, `updateBillingFn`, `getSettingsFn`, `updateSettingsFn`. Inputs validated with Zod. Auth via `requireAuth()`.
  2. Add query-key entries in `src/lib/api/query-keys.ts`: `billing.detail()`, `settings.detail()`.
  3. Replace the bodies of `use-billing` / `use-settings` with `useQuery` + `useMutation` (optimistic merge optional — the README explicitly notes the page doesn't care).
  4. Add a route loader: `loader: ({ context }) => context.queryClient.ensureQueryData(billingDetailQueryOptions())`.
  5. Co-located tests: `_dashboard.billing.test.tsx`, `_dashboard.settings.index.test.tsx`, hooks tests.

### 2.2 Dual path alias (P1)

`tsconfig.json` defines both `@/*` and `#/*` → same target. `package.json` only declares `#/*` for runtime imports.

- **Drift count:** 158 imports use `@/`, 150 use deep `../../../`, ~0 use `#/`.
- **Fix:** pick `@/*`, drop `#/*`, codemod all `../` paths that cross a feature boundary to `@/`. Keep relative imports only **within the same feature folder**.

### 2.3 No enforced layer boundaries (P1)

Files like `features/applications/components/ApplicationCard.tsx` reach into `../../../components/ui/LinkCards` while a sibling uses `@/components/ui/...`. There is no rule preventing one feature from importing another feature.

- **Fix:** add an ESLint rule (`eslint-plugin-boundaries` or `import/no-restricted-paths`) with these layers:
  - `app/` → may import any.
  - `features/<x>/` → may import `lib/`, `components/`, `hooks/`, `server/`, `contexts/`. **Forbidden:** `features/<other>/*`.
  - `components/`, `lib/`, `hooks/` → may import `lib/` only.
  - `server/` → no client-only imports (already implicit via TS).

### 2.4 Test coverage is server-only and shallow (P1)

- **Existing:** 4 files in `__tests__/server/` (applications, articles, auth, github) + one route smoke test.
- **Missing:** every feature, every hook, every UI atom, the other 15 server domains, all Zustand stores.
- **Fix (incremental, not a refactor):**
  - Co-locate new tests next to the file: `Foo.tsx` + `Foo.test.tsx`. Stop adding to `__tests__/` mirror.
  - When you touch a hook in `features/<x>/hooks/`, add a `*.test.ts` next to it as part of the change.
  - Bare minimum to add now: `lib/stores/*.test.ts` (pure logic, fast wins) and a smoke test per route under `app/*.test.tsx`.

### 2.5 `components/` bucket is mixed (P2)

`components/ui/` has 25 files ranging from generic atoms (`Button`, `DropDown`) to app-specific molecules (`PipelineNotificationWatcher`, `DashboardDrawer`, `HeaderNav`). Some belong in features.

- **Fix when you next touch one:**
  - **Reusable atom?** stay in `components/ui/`.
  - **Layout/composition?** stay in `components/layouts/`.
  - **Used by exactly one feature?** move into that feature's `components/`.
  - Suspects to relocate: `PipelineNotificationWatcher` → `features/ai-agent/components/`. `DashboardDrawer` / `HeaderNav` → `components/layouts/` if they truly back AppLayout.

### 2.6 Duplicate `ResumeForm.tsx` (P2)

- `src/components/resume/ResumeForm.tsx`
- `src/features/resumes/components/ResumeForm.tsx`

Two implementations of the same concept is the cleanest DRY violation in the repo. Decide which is canonical — most likely the feature copy — and re-export or delete the other. Same applies to `ResumePreview.tsx` vs `ResumePreviewDrawer.tsx`.

### 2.7 Hook directory split (P2)

- `src/hooks/use-admin-{applications,articles,comments}.ts` — these are clearly feature-bound.
- `src/features/<x>/hooks/` — same role.

Result: a developer searching for an applications hook has two places to look.

- **Fix:** move `use-admin-*.ts` into the matching feature's `hooks/`. Keep `src/hooks/` only for **truly cross-feature** hooks (e.g. `useTheme.ts`, `use-pdf-download.ts` — both qualify).

### 2.8 Naming inconsistency (P3)

- Component files: PascalCase ✅
- Hook files: kebab-case ✅
- Type files: mixed — `applications.types.ts`, `ApplicationTypes.ts`, `AIAgentTypes.ts` (camel/Pascal mid-feature, kebab in `lib/types/`).
- **Fix:** pick one — recommend `*.types.ts` lowercase across the repo. Apply when files are touched.

## 3. Best-practices checklist (use during refactors)

Pin this list. When you open a file to refactor, run through it.

### Imports & aliases
- [ ] Cross-feature/cross-folder imports use `@/...` (never `../../../`).
- [ ] Within-feature imports use relative paths (`./Sibling`, `../components/X`).
- [ ] No imports from another feature's internals — go via `lib/` or share the type.

### Feature folder shape
- [ ] `src/features/<name>/` contains only what is bound to that feature.
- [ ] Optional subfolders: `components/`, `hooks/`, `lib/`, `server/` (rare), `*.ts` for `validation`, `queries`, `types`, `content`.
- [ ] One **public** entry per feature is ideal (`index.ts` re-exporting page-level components). Today only `home/HomePage.tsx` and `account/billing|settings/<Page>.tsx` follow this — consider an `index.ts` per feature when refactoring.

### Routes (`src/app/`)
- [ ] Route file is **thin**: parses `useSearch`/`useParams`, mounts a feature component, no business logic.
- [ ] Search params validated with Zod (`validateSearch`).
- [ ] Loaders use `queryClient.ensureQueryData` with the keys factory in `lib/api/query-keys.ts` — never inline a query key string.

### Server fns (`src/server/`)
- [ ] One file per domain. No client-only imports.
- [ ] Auth via `auth-guard.ts` middleware, not ad-hoc.
- [ ] Inputs validated with `inputValidator(zodSchema)`.
- [ ] Errors thrown as typed objects so the client side can map them.
- [ ] A `*.test.ts` exists next to the file when refactored.

### Components
- [ ] Generic atom → `src/components/ui/`.
- [ ] Layout/page chrome → `src/components/layouts/`.
- [ ] Anything tied to one feature → that feature's `components/`.
- [ ] Props are `readonly`, derived state via `useMemo`/`useTransform` (Motion rule), no inline objects on hot paths.
- [ ] Co-located test file: `Foo.test.tsx`.

### State
- [ ] Server state → React Query, key from the factory.
- [ ] Cross-feature client state → Zustand store in `lib/stores/`.
- [ ] Local UI state → `useState` / Context only when truly cross-tree.

### Tests
- [ ] Co-located with source (`Foo.tsx` + `Foo.test.tsx`).
- [ ] Zustand stores have unit tests (cheapest wins).
- [ ] Hooks tested with `@testing-library/react renderHook`.
- [ ] Server fns tested by mocking `@tanstack/react-start` (pattern already exists in `__tests__/server/applications.test.ts:11-30`).

### DRY guardrails
- [ ] Before adding a util, grep `lib/` and `hooks/` for it.
- [ ] Before adding a type, check `lib/types/<domain>.types.ts`.
- [ ] Before adding a UI atom, check `components/ui/`.
- [ ] If a section/component appears twice, extract it on the second occurrence — not the third (avoid premature abstraction, but two is the trigger here because of the existing duplication risk).

## 4. Refactor sequencing (when ready)

Don't do this all at once. Each step is independently shippable.

1. **Decide on `features/account/`** (wire it or remove it). Cheapest big win.
2. **Add ESLint boundary rules.** Fail fast on new violations even before fixing old ones.
3. **Drop `#/*` alias**, codemod `../../../*` → `@/*` for cross-feature imports.
4. **Move `use-admin-*` hooks** into their features. One PR per feature.
5. **De-dup `ResumeForm`** and resume primitives.
6. **Sweep `components/ui/`** — extract feature-specific molecules to their feature.
7. **Co-locate tests on touch.** New test policy: any file you edit, you co-locate or add a test next to it.

## 5. Anti-patterns to avoid going forward

- Adding a new file under `src/components/ui/` that imports from `src/features/`. UI atoms must not know about features.
- Adding a new server fn without a colocated test mock pattern.
- Inline query keys (`useQuery({ queryKey: ['x', id] })`). Always go through `lib/api/query-keys.ts`.
- Cross-feature imports (`features/applications/...` importing from `features/articles/...`). If shared, hoist the shared piece into `lib/` or `components/`.
- Adding a context where a Zustand store fits — the codebase has only one context (`ThemeContext`) by design.
- Re-introducing `framer-motion`. Project rule (`.claude/rules/motion-react.md`) is `motion/react` only.
